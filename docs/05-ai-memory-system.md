# 05 AI 记忆与上下文引擎

## 1. 设计目标

让 AI 在长篇创作中引用已确认的设定、前文和剧情状态，同时防止模型臆造事实或将错误推断写入正式记忆。

## 2. 记忆分层

1. 作品级规则：题材、风格指南、核心冲突、叙事视角、创作禁忌、世界规则。
2. 结构化实体：人物、地点、组织、物品、规则及其别名。
3. 动态状态：伤势、位置、物品持有等。每条状态可以有可空的生效起止说明。人物关系是独立的关系行，不是塞进档案 JSON 的一段话。
4. 大纲和剧情状态：全书、分卷、章节和场景规划。
5. 章节摘要与事实：关键事件、重要决策、人物变化、证据原文。
6. 当前上下文：当前正文、前章结尾、相关章节片段和本次指令。

## 3. ContextCompiler 的输入

实现在 `backend/app/services/context_builder.py`。创建 AI 任务和「查看本次上下文」都调用 `compile_context`。模拟模型不能绕过。

- novel_id / chapter_id / target_revision
- task_type
- user_instruction
- selection_text（如适用）
- constraints
- context_budget（默认 6000，按字符估算）
- pinned_include / pinned_exclude（只影响这一次）
- 已确认的作品大纲、故事线摘要、当前卷大纲、当前章节大纲和场景卡片
- 当前章节与相邻章节
- 名称或别名命中的实体、其最新状态，以及连到这些实体的人物关系
- 关键词命中的事件、关联到当前或相邻章节的伏笔
- 现行章节摘要
- 作品风格指南与创作约束

编译器只准备材料。它不写正文、正式设定或大纲。

作品还没有任何章节摘要时，编译仍然成功，并在 `warnings` 里说明这次只用了相邻章节，长篇记忆还没写上。已有摘要但没有能当作现行前文的摘要时，也会说明本次仍主要依靠相邻章节。摘要、命中的实体状态和未回收伏笔按预算注入；预算不够时先丢掉较远的摘要。

## 4. 上下文构建优先级

默认优先级（数字越小越优先保留）：
1. 系统安全规则、本次指令和本次任务约束。
2. 作品级硬规则和当前章节约束。
3. 已确认的作品大纲、故事线、卷大纲、章节大纲和场景卡片。
4. 上一章结尾。
5. 名称或别名命中的已确认设定。
6. 相邻后章开头、已确认事件、相关伏笔。
7. 较远章节的现行摘要。
8. 不确定推断（必须显式标记，不得伪装成事实）。

预算不够时，先去掉可丢弃的低优先级材料，并写下排除原因。上一章结尾这类引用可以截短，但必须在警告里说明。作品硬规则、已确认大纲和场景卡片不能截成约 80 字后不声不响地送进去。放不下时保留全文，并在 `warnings` 里说明。用户固定纳入的材料同样不能悄悄丢掉。

两个高权威来源不互相覆盖。若本次指令或约束与已确认大纲里的禁止揭露信息重叠，编译器同时保留两边并给出冲突警告。

作品元信息里已经写下的核心冲突，和题材、文风一起放在作品硬规则中。还没确认的创意、世界观和人物候选不会进入上下文。详见 [引导式创意](14-guided-ideation.md)。编年史规划的候选同样不进入上下文；已经写入的正式事件才会，并带上故事时间。还没关联章节的事件会写明「尚未关联章节」。详见 [编年史](15-chronicle.md)。

章节正文修订变化后，该章已确认大纲和场景卡片变为 `stale`。过期大纲、过期摘要，以及来源修订落后于章节当前修订的状态和事件，都会出现在警告或排除原因里。

## 5. 检索策略

第一版没有向量库，也没有 SQLite FTS：
- 精确匹配：人物名、别名。命中原因会区分「实体名称命中」和「实体别名命中」。
- 有限的 `LIKE`：从指令、选区和一小段正文里取 2 到 6 个汉字，去匹配事件描述或证据。这不是语义检索。
- 相邻章节：上一章结尾、下一章开头。选区改写默认不带下一章开头和较远摘要。
- 规划：只默认纳入 `counts_as_fact=true` 的行。
- 伏笔：当前章或相邻章引入、计划回收，或文本里出现已匹配的名字、指令中的词。
- 同一 `novel_id`，排除已软删除的章节和设定。其他作品的编号即使被固定纳入，也只返回「不存在或不属于这本作品」，不读取那边的正文。

故事线和卷大纲还没有表。编译器留了一个空的钩子，不从那里取数据。人物关系不是图查询：只有当关系的一端已经被名称或别名命中时，才把这条关系放进上下文，并带来源、证据和「故事时间未填写」之类的说明。其他作品的关系不会进入。有效时间只在状态行上有文字时才写进材料；空着就不编造时间。

后续只有在检索效果被评测证明不足时，再引入 embedding / 向量检索。

## 6. 记忆提取与审核

章节保存后可启动分析：
1. 读取确定的章节 revision。
2. 模型提取候选事件、人物状态变化、事实、伏笔和疑似冲突。
3. 每个候选项必须包含 source chapter、source revision、证据原文和 certainty。
4. 无法提供证据的候选项标记为 inferred / uncertain。
5. 主动分析生成 memory_change_proposals，不直接修改正式实体和事件。续写沉淀是下面单独说明的例外。
6. 用户接受后执行事务性更新；拒绝后保留审阅记录。
7. 章节 revision 改变后，相关摘要、待审核提案，以及该章已确认的章节大纲、场景卡片和所在卷的已确认卷大纲标记为 stale。作品级大纲不因此自动过期。摘要和大纲要重新确认后才再次当作事实。
8. 接受 `entity_update` 时记录字段级变更。撤回只把这些字段改回接受前的值。后来改过的字段会导致整次撤回失败，正式设定保持不动。只有整份旧快照、没有字段级记录的提案拒绝自动撤回。

续写候选生成后，以及任意候选被采纳写入章节后，后台用本地提取刷新该章现行摘要，并套用已有提取器产出的人物、事件和伏笔。这一步不调用模型。写入仍走提案的 apply 路径，提案记为已接受，可以撤回。同一修订、同一摘要不会重复插入。主动分析和轻量检查仍只产生待审核提案，不跳过确认。

设定页把实体、关系、动态状态、事件、摘要和提案放在同一处，可以按实体、章节、关系上的故事线标签和状态筛选。证据原文和来源章节保持可见。推断、待审核和已确认用 certainty 与提案状态区分。主动分析时模型不能跳过确认。

正文与资料同步仍写在同一套提案上。作者可以主动做完整分析；章节第一次标成定稿时也会做一次完整分析。手动保存后做轻量检查，自动保存不调用模型。轻量检查只产生关系、伏笔、设定补充和潜在冲突候选。确认或修改后确认才更新正式资料。忽略和延后不写。有意安排的矛盾只改变候选状态；潜在冲突在确认或标成有意矛盾时记成质量问题。详见 [正文与资料同步](13-manuscript-material-sync.md)。

## 7. 冲突检测规则

冲突检测只能输出“疑似冲突”，不能自动改稿。结果应包含冲突类型、当前正文片段、可能冲突的已确认事实、来源章节与引用、严重程度、置信度、建议人工处理方式。

不得仅因人物状态发生变化就认定矛盾。有效时间留空时，状态先后变化不是冲突。规则检查会在两段状态都写了有效时间、且时间重叠或写成同一段文字但取值不同时，记一条时间连续性疑似问题。时间文本解析不了时，问题的 `evidence_status` 为 `insufficient`，文案写明证据不足，不把它说成已经证实的矛盾。人物关系只有在正文明确否定已记录的关系类型时才报告，不判断性格。详见 ADR-009。

同一套规则还区分三类结果。出生或死亡时间与事件时间能比较且冲突，是确定性错误。身份或经历在重叠时段取值不同，也是确定性错误；时间对不上则是疑似矛盾。死亡之后又出现可比较的新状态是确定性错误，时间不够则是疑似。正文直接否定世界规则是确定性错误；只出现例外或也许可以打破，是创作风险。同一方向两条关系类型不同，两边都有原文时是确定性错误。伏笔的回收章节早于埋设章节是确定性错误。向读者揭示早于埋设、或角色发现早于事件实际发生，是疑似矛盾。已确认的暗线隔了至少四章不再出现，是创作风险。伏笔的发生时间、埋设位置、角色发现、读者揭示和回收状态保持分开。

## 8. Prompt 版本管理

- 每类任务有独立模板，例如 `continue_chapter_v1`、`rewrite_selection_v1`、`summarize_chapter_v1`。
- 任务记录模板版本。
- 提示词中区分正文、设定、用户指令和引用材料。
- 小说正文中的指令性文本视为不可信内容，不允许其覆盖系统任务规则。
- 生成结果必须经过长度、空结果、格式和异常响应校验。

## 9. 验收用例

- 已确认人物事实被召回，并附来源章节。
- 旧摘要在章节修改后变为 stale。
- 拒绝提案后正式设定不变。
- 接受提案后状态更新，且来源可追溯。
- 模型输出无证据的新人物身份时不得自动成为正式设定。
- 检索上下文不跨小说串数据。人物关系也只取当前作品、且关联到已命中设定的行。
- 设定更新的撤回不会盖掉接受之后的手工修改。没有字段级记录时拒绝撤回。
- 超出上下文预算时保留当前章节约束、硬规则和已确认大纲，并给出警告，而不是把硬规则截到约 80 字。
