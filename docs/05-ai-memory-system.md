# 05 AI 记忆与上下文引擎

## 1. 设计目标

让 AI 在长篇创作中引用已确认的设定、前文和剧情状态，同时防止模型臆造事实或将错误推断写入正式记忆。

## 2. 记忆分层

1. 作品级规则：题材、风格指南、叙事视角、创作禁忌、世界规则。
2. 结构化实体：人物、地点、组织、物品、规则及其别名。
3. 动态状态：伤势、位置、物品持有、人物关系阶段等。
4. 大纲和剧情状态：全书、分卷、章节和场景规划。
5. 章节摘要与事实：关键事件、重要决策、人物变化、证据原文。
6. 当前上下文：当前正文、前章结尾、相关章节片段和本次指令。

## 3. Context Builder 的输入

- novel_id / chapter_id / target_revision
- task_type
- user_instruction
- selection_text（如适用）
- 当前大纲
- 当前章节与相邻章节
- 相关实体及状态
- 相关摘要、事实和事件
- 作品风格指南与创作约束
- 模型上下文窗口预算

## 4. 上下文构建优先级

默认优先级：
1. 系统安全规则与本次任务约束。
2. 用户本次明确指令。
3. 作品级硬规则。
4. 当前章节大纲和最近前文。
5. 与当前场景相关的已确认事实。
6. 远距离章节摘要。
7. 不确定推断（必须显式标记，不得伪装成事实）。

在预算不足时，先裁剪低相关度的远距离摘要，不能优先删除本章硬约束、人物当前状态或前文衔接信息。

## 5. MVP 检索策略

第一版不强制向量数据库：
- 精确匹配：人物名、别名、地点、道具。
- SQLite FTS 或简单全文检索：章节、摘要、设定文本。
- 最近邻章节：前一章、当前卷相邻章节。
- 元数据过滤：同一 novel_id，排除已删除内容。
- 相关性排序：名称精确匹配 > 当前大纲相关 > 近期章节 > 关键词命中 > 较远摘要。

后续只有在检索效果被评测证明不足时，再引入 embedding / 向量检索。

## 6. 记忆提取与审核

章节保存后可启动分析：
1. 读取确定的章节 revision。
2. 模型提取候选事件、人物状态变化、事实、伏笔和疑似冲突。
3. 每个候选项必须包含 source chapter、source revision、证据原文和 certainty。
4. 无法提供证据的候选项标记为 inferred / uncertain。
5. 生成 memory_change_proposals，不直接修改正式实体和事件。
6. 用户接受后执行事务性更新；拒绝后保留审阅记录。
7. 章节 revision 改变后，相关摘要和提案标记为 stale，要求重新分析或人工确认。

## 7. 冲突检测规则

冲突检测只能输出“疑似冲突”，不能自动改稿。结果应包含冲突类型、当前正文片段、可能冲突的已确认事实、来源章节与引用、严重程度、置信度、建议人工处理方式。

不得仅因人物状态发生变化就认定矛盾。

## 8. Prompt 版本管理

- 每类任务有独立模板，例如 `continue_chapter_v1`、`rewrite_selection_v1`、`summarize_chapter_v1`。
- 任务记录模板版本。
- 提示词中区分正文、设定、用户指令和引用材料。
- 小说正文中的指令性文本视为不可信内容，不允许其覆盖系统任务规则。
- 生成结果必须经过长度、空结果、格式和异常响应校验。

## 9. 验收用例

- 已确认人物事实被召回，并附来源章节。
- 旧摘要在章节修改后变为 stale。
- 拒绝提案后正式设定不变。
- 接受提案后状态更新，且来源可追溯。
- 模型输出无证据的新人物身份时不得自动成为正式设定。
- 检索上下文不跨小说串数据。
- 超出上下文预算时保留当前章节约束和最近前文。
