# ADR-015：编年史沿用故事事件

## 状态

已采纳

## 背景

正式事件已经在 `story_events` 里。正文分析接受 `story_event` 提案后才会写入。设定页能列出这些事件，但是按创建时间倒序，章节必填，参与者只是文本，也没有故事线或伏笔的关联。发布方案要求作品有可读的编年史，事件按发生时间排列，可以手写，也可以让模型帮忙规划，而且模型结果要确认后才进入正式事件。

记忆提案必须带源章节。还没写进某一章的规划用不上那条约束。另建一张正式事件表又会和圣经里的事件分成两套。

## 决策

1. 不改 `0001`–`0014`。新迁移是 `0015_chronicle`。`story_events` 增加可空的 `title`、`sort_order`、`participant_entity_ids`、`story_arc_id`、`foreshadowing_id`，并把 `chapter_id` 改为可空。旧行这些新列为空，原有章节不变。
2. 正式编年史就是未删除的 `story_events`。不新建第二张事件表。`GET /novels/{id}/chronicle` 按发生时间排序。能解析的公历、`第N天` 和 `第N章` 分开排序，不折成同一个日历。解析不了的排在后面，`sort_order` 只排这一截。
3. `participants` 继续是文本。人物追溯用可选的 `participant_entity_ids`，并且只能指向同一作品里的人物。名字若和唯一人物同名，保存时补上编号。
4. 章节、故事线、伏笔都是可选关联。填了就必须属于这本作品。
5. 手写的创建、修改和软删除直接写 `story_events`。这些操作不改章节正文和修订。
6. 模型规划写入 `chronicle_candidates`，状态是 `pending`、`accepted`、`rejected`、`deferred`。这张表是确认前的队列，不是编年史本身。确认才插入 `story_events`。忽略和延后不插入。已确认或已忽略的候选再写返回 `409`。
7. 规划经 `app.ai.gateway`。请求可带 `model_config_id`；不传则用默认模型，再否则最近一份已启用的外部模型。`use_mock=true` 不访问网络，也不能绑定外部模型。
8. 上下文不读取候选表。正式事件若还没有章节，材料里写明尚未关联章节。

## 不做

- 不把参与者文本改成实体外键。
- 不把三种时间写法折算成一个日期类型。
- 不把未确认候选写进 `story_events`。
- 不改记忆提案「必须有源章节」的约束。
- 不换技术栈，不引入另一套模型客户端。

## 替代方案

- 新建 `chronicle_events` 再同步到 `story_events`：两套正式事件会对不齐，否决。
- 把规划塞进记忆提案并放宽源章节：会放开所有正文分析提案，否决。
- 用必填日期排序：作者经常还没有日历，会挡住记录，否决。

## 后果

旧库升级后，已有事件仍在，编年史会按它们的故事时间重新排列；没有可解析时间的旧事件排在后面。降级会丢掉尚未关联章节的事件，已有章节的事件描述还在。要去掉新列或候选表，用新的降级迁移，不改 `0015` 的升级历史。
